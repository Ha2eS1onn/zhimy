# AGENTS.md

本文件是每个 Agent 开工前必须读取的项目规则。只写无法从代码或 `plan.md` 中推断的约定。

## 修改后动作

每次对项目文件做出修改后，必须立即更新 `docs/HANDOFF.md`，记录：

- 本次修改涉及的文件和具体改动
- 关键决策或遇到的坑（如果有）
- 下一步待办事项或阻塞项

不要等到任务结束才写，每次修改完成后立即写入。

## 注释

代码注释可少量。只在以下情况写注释：

- 逻辑不直观、需要解释“为什么这样写”而非“做了什么”
- 存在非显而易见的取舍或临时绕行

不要为显而易见的代码写注释，不要写逐行解释。

## 测试

不要每次修改都运行测试。测试仅在完成一个大环节时进行，例如：

- p1 完成、即将开始 p2 开发时
- 一个功能模块整体收尾时
- 提交或交付前

小步修改期间，依靠 lint / 类型检查做基本校验即可。

## 不确定的信息

遇到不确定的信息必须提问，不要自行假设后继续。包括但不限于：

- 需求边界不清晰、存在多种合理解读
- 技术选型、依赖引入、目录结构调整
- 会影响后续多个环节的决策

提问时说明：不确定的点是什么、你倾向哪种方案及理由、需要我确认什么。

## 交接与状态

任务状态统一记录在 `docs/HANDOFF.md` 中，不单独维护 `TASKS.md`。`docs/HANDOFF.md` 需同时承载：

- 上一轮做了什么（改动、决策、坑）
- 接下来做什么（下一步具体动作、阻塞项）

“下一步”要写到可直接开工的粒度，不要写“继续重构”这类模糊描述。

## HANDOFF.md 写作规范

`docs/HANDOFF.md` 是跨 Agent 交接的唯一入口。每次修改后立即更新，只写"事实 + 决策 + 下一步"。

- **按现有章节结构写**，不要增删章节；新内容归入最匹配的章节，没有匹配的就先问我
- **状态只用** ✅ 完成 / 🟡 进行中 / ⏳ 待验收 / ❌ 未开始，不用"基本完成"这类模糊词
- **"已完成"必须带证据**：文件路径、commit hash、测试用例数、E2E 通过数，至少一项
- **区分"代码完成"与"验收通过"**：没跑的验收写 ⏳ 并注明缺什么（如"缺真实 Key"）
- **决策记录只追加不改写**：被推翻的保留原条目，原因里注明"已被某日决策取代"
- **已知限制写清"为什么限制"和"代价"**，方便后来者判断是否值得改
- 文件路径用反引号包裹，相对仓库根；不写感想、复盘、会议记录
